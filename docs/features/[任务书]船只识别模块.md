## 3. 目录与出口

已落地结构：

~~~text
autowsgr/application/ui/ships/
├── __init__.py          # 包入口，导出 ShipsService / ShipInfo / ShipType / ShipTaskType
├── service.py           # 唯一出口：ShipsService
├── types.py             # 舰种枚举 ShipType 与识别域枚举 ShipTaskType
└── models/              # 各识别域，一个域一个文件
    ├── __init__.py      # ShipInfo —— 所有域共用的槽位事实
    └── exercise.py      # 演习对手域：ROI + 识别 + 后处理
~~~

约定：

- 一个域一个文件，统一放在 `models/` 下；ROI 常量写在域文件顶部，**不另建 constants.py**
  （与已完成的 checker 单文件化一致）；
- `types.py` 只放枚举，`models/__init__.py` 只放各域共用的事实模型（当前是 `ShipInfo`），
  两者都不放识别逻辑；
- 新增域只需在 `models/` 加一个文件、在 `service.py` 加一条路由，不动别的域；
- 包入口 `__init__.py` 直接导出四个公开名字。navigation 留空 `__all__` 是因为它的 `states` 与
  `controller` 互相依赖，ships 没有这种反向依赖，不必照搬；
- `service.py` 从 `ships.models.exercise` 直接导入 `recognize_rivals`，不经过包属性，避免包初始化期的循环。

## 4. 出口契约

### 4.1 形态

与 `NavigationService` 一致：构造时绑定 `ContextHandle`，方法上做识别。

~~~python
from autowsgr.application.ui.ships.service import ShipsService
from autowsgr.application.ui.ships.types import ShipTaskType

ships = ShipsService(ctx)
rivals = ships.recognize_ships_info(ShipTaskType.EXERCISE)
~~~

### 4.2 签名

~~~python
def recognize_ships_info(
    self,
    task_type: ShipTaskType,
) -> tuple[ShipInfo, ...]:
~~~

**入参**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `task_type` | `ShipTaskType` | 是 | 域路由。当前只支持 `ShipTaskType.EXERCISE`，其余值抛 `ValueError` |

未来域需要自己的参数时（例如船池的搜索关键字）在对应域落地时再加，**本版不预留**。

**出参**

`tuple[ShipInfo, ...]`，按槽位号升序排列。长度由域决定：演习对手固定 6 项，船池按实际可见卡片数。

### 4.3 ShipInfo

~~~python
@dataclass(frozen=True, slots=True)
class ShipInfo:
    slot: int                          # 槽位号，从 1 开始，不是 list 索引
    name: str | None = None            # 船只名称；该域不读时为 None
    ship_type: ShipType | None = None  # 舰种；识别失败或不在枚举内时为 None
    level: int | None = None           # 等级；识别失败时为 None
~~~

三条硬约定：

1. **槽位号从 1 开始**。六个槽位是 1–6，不出现 0。
2. **槽位不丢**。识别失败的槽位仍然出现在结果里，对应字段为 `None`。
   调用方据此区分「这个槽位没识别出来」和「这个槽位不存在」。
3. **域不读的字段就是 `None`**。演习对手域不读舰名，六项的 `name` 全是 `None`。

### 4.4 调用示例

~~~python
from autowsgr.application.ui.ships.service import ShipsService
from autowsgr.application.ui.ships.types import ShipTaskType

ships = ShipsService(ctx)
for fact in ships.recognize_ships_info(ShipTaskType.EXERCISE):
    print(fact.slot, fact.ship_type, fact.level)
# 1 轻母 110
# 2 轻母 110
~~~

### 5.1 视觉素材（已实测，未入库）

| --- | --- | --- |
| 1 | 368,414,416,438 | 368,438,422,455 |
| 2 | 505,414,553,438 | 505,438,559,455 |
| 3 | 643,414,691,438 | 643,438,697,455 |

| 5 | 918,414,966,438 | 918,438,972,455 |
| 6 | 1056,414,1104,438 | 1056,438,1110,455 |

实测结论（FastOCR，`RecognitionProfile.SINGLE_LINE`）：6 个槽位全部读出 `轻母` / `LV.110`，
无漏字、无国籍括号、无星级混入。

> 归一化取四位小数后，`0.5750 × 720` 的浮点结果是 413.99…，`int()` 向下取整得 **413**，
> 比上表实测的 414 多含 1px 空白。这正是规范要求的「上边界向下取整、区域不小于目标」，
> 用归一化常量重跑同一张图，六个槽位仍全部读对。

舰种框**不含国籍**（与 `(` 留 1px），等级框**不含星级**（与第一颗星留 2px）。
这是纯 OCR 识别区，**不套用模板的 1px-expanded 约定**（那规则只对模板匹配生效）。

坐标文件：`C:/ShiinaKuroko/01.Project/debug/nav/模板制作/演习页_模板/浮窗文字ROI_720P.yaml`

### 5.2 读法

`common.vision.expect_ocr` 的 `roi` 支持传序列：**一帧截图内逐个区域识别**，
返回 `list[list[TextDetection]]`，分组顺序与 roi 顺序一致。

因此：

- 舰种：一次 `expect_ocr(ctx, roi=<6 个舰种 ROI>, recognition_profile='single_line')`
- 等级：一次 `expect_ocr(ctx, roi=<6 个等级 ROI>, allowlist='LV0123456789.', recognition_profile='single_line')`

两次调用 = 2 帧截图。浮窗是静态的，两帧没有影响。
`attempts=1` 即「读一帧」，不等。

ROI 顺序与槽位号的映射：元组第 1 项就是槽位 1，第 6 项是槽位 6。

### 5.3 后处理（ships 自己负责）

1. **舰种**：`ShipType` 是 `StrEnum`，`value` 就是中文（`CVL = '轻母'`、`SS = '潜艇'`）。
   把同一 ROI 内所有 `TextDetection` 的文本拼起来，与各成员 `value` 逐一严格相等比较，命中即得枚举。
   OCR 把「轻母」读成「轻由」时自然返回 `None`，不需要手写纠错表；
   同一区域被切成多段识别结果时，拼接后仍能命中。
2. **排除 `Other`**：`ShipType.Other = '其他'` 是兜底值，不是真实舰种，比较时跳过。
3. **只认枚举内的值**：OCR 返回的任何不在 `ShipType.value` 里的文本都丢弃，不做模糊匹配、不做别名字典。
4. **等级**：从 `LV.110` 里取数字；取不到返回 `None`。

### 5.4 规则判定（不进 ships）

`CVL > 1`、`SS >= 1` 这类用户特殊规则，**由业务层在拿到 `tuple[ShipInfo, ...]` 之后自己判**。

ships 的出口不接收规则参数，也不返回「合格 / 不合格」，只返回事实。

理由：规则会变（今天是舰种数量，明天可能是等级上限、舰名黑名单），写死在识别层就是给它绑业务债；
而且规则可测性差——识别层的单测应该只断言「读到了什么」，不该断言「这组船该不该打」。

业务层需要规则表时，那是 `business/combat/exercise` 自己的事。

### 6.1 `TaskType` 的替代：`ShipTaskType`

原计划 `recognize_ships_info` 直接收 `autowsgr.server.schemas.TaskType`，实测走不通：
`server/schemas.py:10` 从 `business.combat.fleet` 取 `ALLOWED_SHIP_TYPE_CODES`，而
`business/combat/fleet.py:14` 依赖已不存在的 `autowsgr.common.fleet_types`，
`server.schemas` 当前整体 `ImportError`。ships 若直接引用它，整个包会一起炸。

因此 `ships/types.py` 自带一个最小枚举：

~~~python
class ShipTaskType(StrEnum):
    """船只识别按任务类型划分的识别域。"""

    EXERCISE = 'exercise'
~~~

成员值与 `TaskType` 逐字一致（`'exercise'`），等 `server.schemas` 修好后可直接替换，
`recognize_ships_info` 的调用形态不用变。

`ShipType` 已迁入 `ships/types.py`，`business/combat/types.py` 里的定义已删除；
10 个真实引用点（`config.py` 与 9 个 controller 文件）已改到新位置。
仍从已删除的 `autowsgr.common.types` 导入 `ShipType` 的 8 处存量坏账不在本次范围。
