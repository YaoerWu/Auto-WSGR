## 0. 这份任务书解决什么

战斗模块是整个项目最核心、也是现在最散的一块。代码散在五个地方（`application/combat`、`business/combat`、`application/ui/controller/operations/sortie_page`、`application/vision`、`config*.py`），**全链路 import 都跑不通**，只能读不能跑。

要重写，先得把「上一代到底在干什么」完整记下来，否则重写会凭印象漂移。本文档分两半：

- **第 1 章**：战斗引擎的业务逻辑全貌（业务流程、状态机、判定规则、退出条件）。
- **第 2–4 章**：这些代码现在散在哪、为什么跑不起来、收进 combat 包要收哪些。

## 1. 战斗引擎现在到底在干什么

### 1.1 它管哪一段

**只管「打仗」。** 从出征准备页点了「开始出征」起，到回到地图页（或大破回港、船坞满）为止。进图、选章、换船、补给、修理全在它外面。

本质是一个循环：

```text
看屏幕 → 认出当前是哪个界面 → 按计划决定点什么 → 点 → 再看屏幕
```

对外只有一个入口，形态与 `fleet_select.adjust_fleet` 一致：输入参数 → 内部跑完一整场 → 返回结果。中间不分段、不外抛、不等外部指令。

### 1.2 一次出击的全景（四步）

`NormalFightRunner.run()`（`autowsgr/business/combat/bettle/normal_fight.py:127`）就四句：

```text
【1】进图    _enter_fight()          normal_fight.py:322
      常规战：出征页 → 选章 → 选图 → 进图          _enter_normal   :329
      活动战：活动地图页 → 选难度 → 选入口 → 进图   _enter_event    :363
         │
         ▼
【2】准备    _prepare_for_battle()   normal_fight.py:375
      换船 → 补给 → 修理 → 读 6 条血条 → 点「开始出征」
      产出：6 个槽位的伤情，作为战斗引擎的初始血量
         │
         ▼
【3】打仗    CombatEngine.fight()    application/combat/engine/engine.py:85
      状态机循环，直到拿到「结束」标志
         │
         ▼
【4】收尾    _handle_result()        normal_fight.py:561
      船坞满 → 按配置自动解装；其它 → 交给上层统计次数／战利品
```

两条容易被忽略的规则：

- **上一轮真的打完（`OPERATION_SUCCESS`），下一轮才跳过「选难度/选入口」检查**（`normal_fight.py:118` 的 `_skip_check`、`:182` 赋值）。因为战后回港必落在关卡浮层态。中途被打断或失败，下一轮恢复完整检查。
- **出征前 6 个槽里出现大破，直接抛 `ActionFailedError('出征前检测到大破舰船，退出程序')`**（`normal_fight.py:425-427`），不进入战斗。

### 1.3 核心循环

`CombatEngine.fight()`（`engine.py:166`）的 while 只有 20 行：

```text
        ┌────────────────────────────────────────────────────┐
        │ 当前状态 phase ＋ 上一次点的动作 last_action        │
        └───────────────────┬────────────────────────────────┘
                            │ resolve_successors(plan.transitions, phase, last_action)
                            ▼
                  「下一步可能出现哪几个界面」
                            │
                            ▼
        ┌────────────────────────────────────────────────────┐
        │ 轮询认界面 wait_for_phase()                        │
        │   每轮：① 先跑本轮小动作（点加速／追船位／关资源弹窗）│
        │         ② 再拿候选界面逐个比模板                   │
        │   认出 → 进入该状态                                │
        │   超时 → 抛 CombatRecognitionTimeoutError          │
        └───────────────────┬────────────────────────────────┘
                            ▼
        ┌────────────────────────────────────────────────────┐
        │ 派发 _PHASE_HANDLERS[phase] → self._handle_xxx()   │
        │ 处理器 = 读数据 ＋ 点按钮 ＋ 记一条 CombatEvent    │
        └───────────────────┬────────────────────────────────┘
                            ▼
              返回标志：继续 / 结束 / SL / 船坞满
```

返回标志怎么翻译（`engine.py:180-192`）：

```text
FIGHT_CONTINUE  → 继续下一轮循环
FIGHT_END       → 跳出，标记 OPERATION_SUCCESS
SL              → 跳出，标记 SL（要求上层重开这一场）
DOCK_FULL       → 跳出，标记 DOCK_FULL（交给上层决定解装）
```

另外两个异常出口：

```text
用户点了停止   → CombatStopRequestedError    → 直接当 FIGHT_END（engine.py:169-172）
识别超时       → _try_recovery()（engine.py:301）：睡 3 秒，只找「结束页」
                 找到了 → 继续跑
                 没找到 → 标记 SL
```

### 1.4 十二个界面分别认什么、做什么

处理器表在 `autowsgr/application/combat/engine/phase_handlers.py:39`（`_PHASE_HANDLERS`），**表里 12 项**。`CombatPhase` 另有一个 `START_FIGHT` 不在表里——它永远识别不出来，只当转移图起点（见本节末第 1 条）。

| 状态 | 认出什么 | 处理器干什么 | 实现所在层 |
| --- | --- | --- | --- |
| `DOCK_FULL` | 船坞已满弹窗 | 记事件，返回船坞满 | application `:320` |
| `FIGHT_CONDITION` | 战况选择界面 | 点计划里的战况，记 `last_action` | application `:119` |
| `SPOT_ENEMY_SUCCESS` | 索敌成功页（敌编成） | 读敌编成＋敌阵型 → 撤／迂回／打 | **business** `decision.py:56` |
| `FORMATION` | 阵型界面（像素签名 `CHOOSE_FORMATION_SIGNATURE`） | 按规则选阵型，含两种 SL 分支 | **business** `decision.py:154` |
| `MISSILE_ANIMATION` | 导弹支援动画 | 跳过动画 | application `:136` |
| `FIGHT_PERIOD` | 昼战／夜战动画 | 战斗中只 `sleep(0.5)`；`SL_when_enter_fight` 为真则 SL | application `:143` |
| `NIGHT_PROMPT` | 夜战提示 | 追击／撤退 + 记录 | application `:157` |
| `RESULT` | 评级字母 SS~D | 读评级＋MVP＋各舰血量，然后点继续 | **business** `settlement.py:40` |
| `EXP_SETTLEMENT` | MVP 徽章 **且没有**评级字母 | 点继续推进 | application `:290` |
| `GET_SHIP` | 掉落页 | 幂等抓掉落舰名，再点继续 | application `:295` |
| `PROCEED` | 继续前进／回港提示 | 按 `proceed` ＋ 血量阈值决定前进还是回港 | **business** `decision.py:219` |
| `FLAGSHIP_SEVERE_DAMAGE` | 旗舰大破 | 点确认，直接返回结束 | application `:305` |

两个必须知道的技术细节：

1. **`START_FIGHT` 永远不会被认出来。** 它的签名 `template_key=None` + `pixel_signature=None` + `image_templates=None`（`recognizer.py:86-89`），`wait_for_phase` 里被 `continue` 跳过（`:322-327`）。它唯一的作用是当转移图的起点，决定「刚点完出征，接下来可能看到什么」。
2. **经验结算页靠「有 MVP 但没评级字母」来认。** `CombatPhase.EXP_SETTLEMENT` 用 `template_key=RESULT_PAGE` + `exclude_template_key=RESULT_GRADES`（`recognizer.py:132-137`）。因为 MVP 徽章在战果页和经验页都会出现（实测 0.94+），而评级字母只在战果页出现。

### 1.5 MAP 类：常规战 / 活动战（多节点推图）

转移图由 `_build_map_transitions`（`state.py:134`）生成，`ep` = 结束页。

```text
START_FIGHT （点了开始出征，过渡帧；这期间每轮点加速、追船位、关资源弹窗）
   │
   ├────────────────► DOCK_FULL             船坞满 ──► 退出
   ├────────────────► FIGHT_CONDITION       战况选择
   ├────────────────► SPOT_ENEMY_SUCCESS    索敌成功
   ├────────────────► FORMATION             阵型
   └────────────────► FIGHT_PERIOD          直接开打（没索敌）

PROCEED  行军中的「继续前进 / 回港」提示
   ├─ 前进 ─► FIGHT_CONDITION / SPOT_ENEMY_SUCCESS / FORMATION / FIGHT_PERIOD / 结束页
   └─ 回港 ─► 结束页

FIGHT_CONDITION  战况选择
   └────────► SPOT_ENEMY_SUCCESS / FORMATION / FIGHT_PERIOD

SPOT_ENEMY_SUCCESS  索敌成功页 ★业务决策核心
   ├─ 打 ────► FORMATION / FIGHT_PERIOD / MISSILE_ANIMATION
   ├─ 迂回 ──► FIGHT_CONDITION / SPOT_ENEMY_SUCCESS / FORMATION / FIGHT_PERIOD / 结束页
   └─ 撤退 ──► 结束页

FORMATION  选阵型
   └────────► FIGHT_PERIOD / MISSILE_ANIMATION

MISSILE_ANIMATION  导弹支援动画
   └────────► FIGHT_PERIOD / RESULT

FIGHT_PERIOD  昼战／夜战动画
   └────────► NIGHT_PROMPT / RESULT

NIGHT_PROMPT  夜战提示
   ├─ 追击 ──► RESULT
   └─ 撤退 ──► RESULT

RESULT  战果页（评级 + MVP）
   └────────► EXP_SETTLEMENT      （慢速采集模式 collect_result_info=True，默认）

EXP_SETTLEMENT  经验结算页
   └────────► PROCEED / 结束页 / GET_SHIP / FLAGSHIP_SEVERE_DAMAGE

GET_SHIP  掉落页
   └────────► PROCEED / 结束页 / FLAGSHIP_SEVERE_DAMAGE

FLAGSHIP_SEVERE_DAMAGE  旗舰大破
   └────────► 结束页
```

**索敌页那一步是整场战斗的决策中枢**（`decision.py:56` `_handle_spot_enemy`），业务顺序：

```text
读出敌方编成 get_enemy_info + 敌方阵型 get_enemy_formation
   │
   ├─ 当前节点不在预设白名单？              ──► 点撤退，结束（FIGHT_END）
   │     plan.is_selected_node(self._node)
   │
   ├─ 查规则：先 formation_rules.evaluate_formation(敌阵型)
   │          无结论再 enemy_rules.evaluate(敌编成)
   │         RETREAT   ──────────────────────► 点撤退，结束（FIGHT_END）
   │         DETOUR    ──► 强制迂回（能力不足则抛 ValueError）
   │         FORMATION ──► 记下规则阵型 _formation_by_rule，待会儿选阵型时用
   │
   ├─ 该迂回（计划 detour 且按钮存在）      ──► 点迂回 → 等离开索敌页
   │                                             last_action = 'detour'
   │
   ├─ 计划要求远程导弹支援                  ──► 点 MISSILE_SUPPORT
   │
   └─ 都不满足                              ──► 点「进入战斗」，last_action = 'fight'
```

阵型选择还有三种 SL 分支（`decision.py:154`）：

```text
不在预设点                                   ──► SL
last_action == 'detour' 且迂回失败要 SL       ──► 记 DETOUR 失败 + SL
索敌失败（last_action 不是 fight/detour）：
    SL_when_spot_enemy_fails 为真            ──► SL
    否则用 formation_when_spot_enemy_fails 替代阵型
```

### 1.7 五种模式 = 两个大类 + 一个结束页

配置在 `autowsgr/business/combat/plan.py:199`（`_MODE_SPECS`），转移图由 `:209` 自动派生。

| 模式 | 大类 | 结束页 | 打完停在 |
| --- | --- | --- | --- |
| `normal` 常规战 | MAP | `MAP_PAGE` | 常规地图页 |
| `event` 活动战 | MAP | `EVENT_MAP_PAGE` | 活动地图页 |
| `battle` 战役 | SINGLE | `None` → `RESULT` | 战果页 |
| `decisive` 决战 | SINGLE | `None` → `RESULT` | 战果页 |
| `exercise` 演习 | SINGLE | `EXERCISE_PAGE` | 演习页 |

`end_phase` 是这套设计的中枢：**引擎每派发完一个状态都检查 `phase == plan.end_phase`，是的话记一条「自动返回」事件并直接返回成功**（`phase_handlers.py:105-113`）。所以「什么叫打完了」不是一段判断逻辑，而是配置里的一个字段。

转移图不是手写的，是按 `(大类, 结束页)` 算出来的（`state.py:106` `build_transitions`）。**加一种新战斗模式，只要在 `_MODE_SPECS` 里加一行。**

### 1.8 四条「非正常结束」的路

```text
① 船坞满    START_FIGHT 时探到弹窗
            → 返回 DOCK_FULL
            → 上层 _handle_dock_full（normal_fight.py:572）：
              开了自动解装就弹窗直达解装（destroy_ships_auto from_dialog=True）
              解装成功不翻成功标志，只置 result.dock_full_destroyed = True
              （这一场根本没开打，翻了会被算进次数）

② 旗舰大破  战斗中出现 FLAGSHIP_SEVERE_DAMAGE
            → 点确认，返回 FIGHT_END
            → 上层：这一场算打完了（成功）

③ SL       业务规则要求这一场不算
            触发点：节点不在预设点 / 索敌失败 / 迂回失败 / 进战斗前要求卡点
            → 返回 SL，上层重开这一场

④ 识别超时  认不出画面
            → 睡 3 秒，只找「结束页」
            → 找到了继续；找不到 → SL
```

### 1.9 战果页／经验页／掉落页怎么推进（`_click_result_until_closed`）

这是整套引擎里最容易出事故的一段（`phase_handlers.py:175`），行为约定：

```text
点一下「继续」
   │
   ▼ 复检轮询（默认每次点击后 4 轮 × 0.3 秒）
   在 [当前页] + [允许穿越的过渡页] + [合法后继页] 上判定
   │
   ├─ 认出后继页        → 成功返回
   ├─ 认出过渡页（经验页）→ 继续点，跳过
   ├─ 认出当前页        → 点击被动画吞了，重试点击
   ├─ 认出掉落页        → 先幂等抓掉落，再返回
   └─ 什么都认不出      → **只等不点**
```

「什么都认不出就只等不点」是硬要求：页面正在切换时盲目连点会穿透中间页，落点若是 PROCEED 对话框还会误触按钮。

另外 `_result_successors`（`:263`）比转移图**故意更宽**：转移图描述真实流转，这个集合额外包含「快速连点穿透」的场景，好让复检能提前停下来。

### 1.10 地图上怎么知道船走到哪个点了

纯几何，跟模板匹配无关（`autowsgr/application/combat/node_tracker.py`）。

```text
地图数据：resources/data/map/normal/<章>-<图>.yaml
          （P0 前旧代码把根目录算成 autowsgr/common/data，该目录不存在，
            已在地图追踪搬迁时修正；见 §5.8）
          每个节点 = { 名字, x, y, next_nodes }

每帧（update_ship_position :424 → update_node :458）：
  ① 是索敌页就不更新
  ② 找黄色小船（色块聚类 _find_yellow_cluster）→ 像素校验 _recheck_pixel
  ③ 速度方向 = 上一帧位置 → 这一帧位置（首帧没有，退化成直线距离）
  ④ 候选 = 当前节点 ＋ 当前节点的 next_nodes
  ⑤ 优先：节点落在速度射线的 0.01 范围内 → 取直线距离最小的
     没有落点 → 退化成「射线距离最小」，并列再比直线距离
  ⑥ 变了就更新当前节点
```

地图数据缺 `next_nodes` 就判定失败，原地不动。活动地图走 `MapNodeData.load_event(event_name, chapter, map_id, entrance)`（`:190`），起点 `α`/`β` 都重映射成 `'0'`（`:50`）。

## 3. 结构上的三个病灶

> **状态（2026-11-05 更新）**：三条全部已解决。3.1 在 P0 解决（三个 mixin 全部搬进
> `application/combat/monitor`，不再跨层）；3.2 与 3.3 在本轮收尾解决，见各小节末尾。

### 3.1 处理器表跨层，靠命名约定对齐（P0 已解决）

`_PHASE_HANDLERS`（`application/combat/engine/phase_handlers.py:39`）是「状态 → 方法名字符串」的表，写在 application 层；但 12 个处理器里 **4 个的关键实现在 business 层**：

```text
_handle_spot_enemy   business/combat/handlers/decision.py:56
_handle_formation    business/combat/handlers/decision.py:154
_handle_proceed      business/combat/handlers/decision.py:219
_handle_result       business/combat/handlers/settlement.py:40
```

派发方式：`getattr(self, handler_name)`。宿主类 = `CombatRunner(PhaseHandlersMixin, ApplicationCombatEngine)`，而 `PhaseHandlersMixin(CombatDecisionMixin, CombatSettlementMixin, CombatPhaseHandlersMixin)`（`business/combat/handlers/__init__.py:8`）。

即 application 层是靠着**名字约定 + mixin 继承顺序**去调 business 的方法。表里任何名字改掉，**运行时才 `AttributeError`，编译期发现不了**。而且 `CombatPhaseHandlersMixin` 单独用是残缺的（表里 12 个名字，它自己只有 8 个实现）。

### 3.2 转移图重复构建 + 一份死数据（已解决）

- `CombatPlan.transitions`（`plan.py:375`）是一个 property，**每次访问都 `build_transitions(...)` 重建整张 dict 树**；而引擎每步 `_update_state` 都访问一次。
- `MODE_TRANSITIONS`（`plan.py:209`）按五种模式预建了五张图，**全仓没有任何消费者**（`plan.transitions` 自己重算，不走它）——死数据。
- 另有一处同名不同签名的陷阱：`normal_fight.py:561` 的 `_handle_result(self, result: CombatResult)` 与 `settlement.py:40` 的 `_handle_result(self) -> ConditionFlag` 同名，引擎派发的是后者。

P0 后的实际状况（当时）：

- `MODE_TRANSITIONS` 搬到了 `monitor/transitions.py`，仍然只有 `monitor/__init__.py` 导出、零消费者 —— 病灶原封不动。
- `plan.transitions` 仍然是每次访问都重建（`business/combat/plan.py:327`）。
- 同名陷阱已消失：business 的 `_handle_result` 换了名字，引擎侧只剩一个。

本轮解法（2026-11-05）：

- 删掉 `MODE_TRANSITIONS`；`build_transitions` 改为转发 `_cached_transitions`
  （`functools.cache`），缓存键 = `(大类, 结束页, 采集开关)`。副作用：拿到的是
  同一份 dict，调用方必须只读 —— 已在 docstring 写明。
- `plan.transitions` 不改代码，靠上面这层缓存自然变成 O(1)，且多次访问拿到同一对象。

### 3.3 application 反向依赖 business（已解决）

任务书 §5.5 与 `application/combat/README.md` 都写着依赖方向是
`business → application`，但 P0 落地后引擎反过来 import 编排层：

引擎的输入契约改用 `combat/types.py` 里的 Protocol 描述，不再 import 具体

## 5. 架构定稿（2026-11-05 用户拍板）

### 5.1 边界

| 项 | 内容 |
| --- | --- |
| 输入 | 作战计划（结构上满足 `combat/types.py` 的 `BattlePlan` Protocol）+ 战前舰队血量 `ship_stats` + `ContextHandle` |
| 前提（调用方保证） | 玩家已停在**出征准备页**；舰队已编好、已补给、已修理 |
| 起点 | 点下【开始出征】的那一刻 |
| 内部 | 完整一场战斗。中间不分段、不外抛、不等外部指令 |
| 终点 | 战果页退出，回到出征页 / 演习页 / 活动地图页 / 地图页 |
| 输出 | `CombatResult`（胜负、评级、战后血量、掉落、事件流） |
| 不负责 | 进图选章选难度、编队换船、补给修理、打几场、打完去哪 |

对外只有一个入口：

```python
run_battle(
    ctx: ContextHandle,
    plan: BattlePlan,
    *,
    ship_stats: list[ShipDamageState],
    stop_requested: Callable[[], bool] | None = None,
) -> CombatResult
```

`ctx` 而不是 device：`common.vision` 的截图与 `expect_*` 全部吃
`ContextHandle`，引擎不另造一条设备通道。`plan` 用 Protocol 描述，引擎不
import `business.combat.plan`（原因见 §3.3）。

三步骤：输入参数 → 内部运行 → 得到结果。和选船模块 `adjust_fleet` 同构，不负责编排。

### 5.2 四个领域与 16 个战斗阶段

战斗状态机的全部阶段（`CombatPhase`，`application/combat/engine/state.py:13` 共 16 个）按领域归位，一个不多一个不少：

| 阶段 | 领域 |
| --- | --- |
| `START_FIGHT`（点出征后的过渡：查船坞、进战斗） | ① 准备阶段编排 |
| `DOCK_FULL`（船坞满弹窗） | ① 准备阶段编排 |
| `FIGHT_CONDITION`（战况选择） | ③ 战斗决策 |
| `SPOT_ENEMY_SUCCESS`（索敌成功：打 / 撤 / 迂回） | ③ 战斗决策 |
| `FORMATION`（选择阵型） | ③ 战斗决策 |
| `NIGHT_PROMPT`（夜战：追击 / 撤退） | ③ 战斗决策 |
| `PROCEED`（继续前进 / 回港） | ③ 战斗决策 |
| `MISSILE_ANIMATION`（跳过导弹支援动画） | ② 战斗监控 |
| `FIGHT_PERIOD`（昼战 / 夜战进行中） | ② 战斗监控 |
| `MAP_PAGE` / `EXERCISE_PAGE` / `EVENT_MAP_PAGE`（终点页） | ② 战斗监控（出口） |
| `RESULT`（战果评价） | ④ 战斗结果识别 |
| `EXP_SETTLEMENT`（逐舰经验结算） | ④ 战斗结果识别 |
| `GET_SHIP`（掉落） | ④ 战斗结果识别 |
| `FLAGSHIP_SEVERE_DAMAGE`（旗舰大破强制回港） | ④ 战斗结果识别 |

② 不是某一批阶段，它本身就是主循环：识别当前阶段 → 分派处理器 → 点击 → 再识别，直到终止态。

### 5.3 模式差异只有两个参数

```python
_MODE_SPECS = {
    CombatMode.NORMAL:   (ModeCategory.MAP,    CombatPhase.MAP_PAGE),
    CombatMode.EVENT:    (ModeCategory.MAP,    CombatPhase.EVENT_MAP_PAGE),
    CombatMode.BATTLE:   (ModeCategory.SINGLE, None),
    CombatMode.DECISIVE: (ModeCategory.SINGLE, None),
    CombatMode.EXERCISE: (ModeCategory.SINGLE, CombatPhase.EXERCISE_PAGE),
}
```

五种模式（常规 / 活动 / 战役 / 决战 / 演习）的战斗内流程**完全相同**，差异只有「多节点地图 或 单点」与「退回哪个页面」，由 `build_transitions(category, end_page)` 生成。

**因此 combat 包内不设 models/ 五模式目录。** 模式编排在 combat 外面。

### 5.5 与 business/combat 的分工

- `autowsgr/application/combat/`：战斗引擎。输入参数、内部跑完、给出结果，不负责编排。
- `autowsgr/business/combat/`：编排。决定打几场、打完去哪、什么时候换船与修理。**保留并瘦身**，战斗引擎部分全部迁出。
- `autowsgr/application/controller/sortie/battle_engine/`：战斗链的 checker 与 page（P5 已落地）。

依赖方向必须单向：`business/combat → application/combat → controller/sortie/battle_engine → common/{vision,device,system}`。
`CombatPlan` 与 `from_yaml` 留在 `business/combat/plan.py`，引擎只认
`BattlePlan` Protocol，不 import 具体类（§3.3）。

### 5.6 决战

决战 `_main_loop` 的 12 个阶段里，选船、撤退换船、修理、章节推进、关键点判断都不是战斗，超出 §5.1 的边界。

处理方式：**决战不整体进 combat**。它的战斗部分本来就只调 `run_combat(CombatMode.DECISIVE)`（现状 `business/combat/decisive/handlers.py:499`），章节推进与换船留在编排层。
