### 2.5 页面业务流程（用户 2026-11-01 现场补充，原话转述）

#### 2.5.1 进入页面

1. **到达判断只按 task type 匹配对应的特征模板**——四种准备页各一张特征模板，进了哪张就认哪张，
   不做额外判断（对应 §2.2 已有的四模板 checker）。
2. 进页面之后，**业务层去读 dispatch 的内容**，执行对应的业务流程；UI 层负责用各种操作支撑
   准备页上的动作。

#### 2.5.2 业务动作

**A. 更换编队**

- 业务层传入编队号（1 / 2 / 3 / 4）；
- UI 控制器点击对应队伍 tab，**点击坐标 = 模板匹配中心 + 静态坐标兜底**；
- 流程是**先点击、再确认**（点完要复核是否真的切到该队）。

**B. 快速整备**

- **所有准备页都只提供两个功能：快速补给、快速修理**；
- **快速补给**：识别左下角勾选框是否勾选。已勾选 = 快速补给已开启；未勾选 → 按用户设置决定
  是否勾选开启；
- **快速修理**：两条流程
  - 开启快速修理：直接用页面里的入口去修理；
  - 需要**识别快速修理的数量**，给一个**最低阈值**；低于该阈值走**普通修理**
    （普通修理流程本次不写，先记 TODO）。

**C. 战术支援（全新业务）**

- 点击战术支援（buff）按钮 → 弹出浮窗；
- 浮窗打开时，**战术支援浮窗模板与战术支援按钮模板都能匹配到**（两个同时命中）；
- 浮窗内按钮默认状态是**未开启**；
- 点击开启后：战术支援按钮切换成**已激活**，浮窗内按钮变成**已开启**；
- 浮窗**不会自动关闭**；
- **关闭浮窗的方法**：再次点击用户输入的队伍（例如当前激活 1 队，就再点一次 1 队）。

#### 2.5.3 未来的页面流程

**先检测、再处理**。检测顺序固定为：

1. 检测队伍是不是对的；
2. 检测需不需要打开战术支援；
3. 检测需不需要开启自动补给（游戏内默认会开，但按用户喜好提供一个开关）。

#### 2.5.4 素材

缺的模板由用户陆续补齐（2026-11-01 已补：队伍 tab 四态、战役支援按钮 / 浮窗、综合战力 /
快速修理 / 快速补给三个面板高亮、自动补给未勾选）。

## 4. 设计

### 4.1 目录拆分（用户 2026-11-01 定）

```
autowsgr/application/ui/controller/sortie/battle_preparation/
├── __init__.py          # 只导出 BattlePreparationPage / FleetSelectPanel / QuickMaintenancePanel
├── page.py              # 页面级单次点击（返回；开始出征见 4.5）
├── fleet_select/        # 选队 + 槽位点击
├── campaign_support/    # 战役支援
└── quick_maintenance/   # 快速整备（补给、修理）
```

- `fleet_select`：**负责选择队伍和编成舰队**（用户 2026-11-01 原话）。选队 = 队伍 tab 1–4；
  编成舰队 = 把 6 个槽位调成目标状态。中间编队框的识别与落点复用 `controller/fleet/` 既有能力，
  **不重写**。
  - 子包只有 `__init__.py` 和 `page.py`，**不拆 constants.py**：两套坐标（`FLEET_TAB_CLICKS` 1–4、
    `SHIP_SLOT_CLICKS` 1–6）直接写在 `page.py` 的校准区（用户 2026-11-02 定「constants 先和 page 合并」）。
  - 槽位坐标取**立绘区中心**（y = 333px），不是血条位置（y = 429px）。用户 2026-11-02 实测：
    点卡片哪里都能选中该槽位，所以用立绘中心。
- `campaign_support`：只服务 `CAMPAIGN_PREPARATION`，读支援状态、切开关。
- `quick_maintenance`：补给 + 修理合成一个包（「整备」= maintenance），**素材未到**，等用户补
  ROI 与模板再动。

命名说明：用户要求「只要反映是快速整备就行」，取 `quick_maintenance`；不叫 `quick_prepare`
是因为 prepare 与 `battle_preparation` 撞词。

### 4.3 控制器边界

仍然是「单次点击、不识别、不等待、不重试」。状态读取全部在 checker，落点由调用方传入
（识别中心优先，固定坐标兜底）。

### 4.4 面板联动的 2 秒等待

底部 tab 点击 → 右侧面板动画 1.5s。归属候选：

- **A（倾向）**：等待放在调用方（业务流程或导航边动作），控制器保持纯点击；
- **B**：`quick_maintenance` / `page.select_panel` 自带 `time.sleep(2.0)`。

选 A 的理由：控制器里塞 sleep 会让「点一下」变成黑盒，且 2s 是保守值不是精确值，
等多久应由「要读什么」的一方决定（读面板状态时 checker 自己带 `attempts` / `interval_seconds`）。

### 4.8 血条识别与实机标定（2026-11-02 实机验证）

**血条的读法**：血条用长度表示血量、整条同色，从左到右依次是满血绿、中破黄、大破
橙红；血量耗尽后残留深灰。探针固定在每条血条左端 +12px，读到的是当前状态色，血量再低
也能读到，只有接近空血时才会落到深灰上判大破。

**参考色必须按实机帧标定**。旧框架的参考色取自静态 PNG 截图，实机画面走 scrcpy 解码
（H.264 + YUV 转 RGB），颜色整体比截图暗 10~20，直接用旧值会全部落在容差外。

实机帧实测（1280x720，编队页六艘船，其中 3 号中破、4 号大破）：

| 槽位 | 状态 | 血条实测色 | 旧参考色 | 旧距离（容差 30） | 新参考色 | 新距离 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 / 2 / 5 / 6 | 满血 | `(63, 151, 113)` | `(75, 168, 118)` | 21.4 | `(63, 151, 113)` | 0 |
| 3 | 中破 | `(239, 172, 32)` | `(246, 184, 51)` | 5.9 | `(239, 172, 32)` | 0 |
| 4 | 大破 | `(234, 102, 36)` | `(230, 58, 89)` | **67.2 不命中** | `(234, 102, 36)` | 0 |

单点采样受血条斜纹影响会波动 ±20，满血绿最差采到 `(45, 147, 101)`（距新参考色 22），
仍在新容差内，所以不需要改探针位置或加多点平均。

**实机 E2E 结果**：`detect_layer` 判出「出征准备」，`read_ship_damage` 输出
`{1: normal, 2: normal, 3: moderate, 4: severe, 5: normal, 6: normal}`，与画面一致。
