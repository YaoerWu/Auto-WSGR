# Python 代码编排、注释与业务语义规范（第一版）

## 1. 适用范围

本规范适用于 AutoWSGR 内所有手写 Python 代码，包括生产代码、测试、工具和
examples。目标是让不同维护者和 Agent 写出的代码在文件结构、视觉节奏、命名和
注释表达上保持一致，看起来像由同一个人维护。

本规范只约束：

1. 文件、类、函数、业务代码和常量的编排；
2. import 的位置、分组和使用方式；
3. 函数前缀和业务语义命名；
4. 模块、类、函数、常量和流程注释的格式；
5. 功能区域和流程节点的视觉划分。

本规范不定义架构分层、模块目录模板、具体模块的公开 API、状态所有权、异常策略、
安全、测试范围或 Code Graph 维护。上述内容由项目级规则和各模块专项规范定义；
本规范只补充公开入口与内部实现的通用编排原则。

本文件中的“必须”和“不得”为硬规则。模块专项规范可以增加更具体的约束，但
不得静默改变本规范；确需例外时，专项规范必须写明例外对象和理由。

### 1.1 规范层次与优先级

本项目有三层规则，它们叠加生效、互相补充，不是互相替代：

1. `pre-commit` / Ruff 等工具的自动结果：确定**项目整体格式**。优先级最高，工具改过的
   结果就是正确格式；本规范不得要求与工具自动修复相反的写法。
2. `AGENTS.md`：确定**项目禁止项**。优先级居中，用于拦住工具管不到的红线。
3. 本规范（coding style）与模块专项规范：确定**项目细节**，即编排、命名、注释、日志和
   常量。

三者冲突时按 1 → 2 → 3 的顺序取高优先级者。本规范中凡与工具自动修复结果相反的文字，
以工具结果为准，并应尽快修订本规范；凡与 `AGENTS.md` 禁止项冲突的文字，以
`AGENTS.md` 为准。

## 2. 总体原则

- 文件顺序必须表达阅读顺序和执行顺序，不能按字母机械排序。
- 一个概念必须只使用一套业务词汇，目录、文件、类型、函数、常量、枚举、日志和
  注释必须保持一致。
- 注释必须解释业务意图、关键阶段、判断原因或目标状态，不能翻译下一行代码。
- 代码分区必须按业务功能命名，不能使用“其他”“工具”“辅助一”一类模糊标题。
- 配置必须靠近实际消费者；跨文件共享值与单文件参数不得混放。
- 简单代码保持短，复杂流程靠结构和节点注释表达，不靠超长 docstring 掩盖。

## 3. Python 文件统一骨架

普通 Python 模块必须按以下顺序编排：

1. 模块 docstring；
2. from __future__ import annotations；
3. 标准库 import；
4. 第三方 import；
5. 项目内部绝对 import；
6. if TYPE_CHECKING 类型导入；
7. logger；
8. 文件专属常量和配置；
9. 类型别名、枚举、数据模型；
10. 主要公开类或公开函数；
11. 支撑主要流程的公开实现；
12. 私有辅助函数；
13. __all__，仅在模块确实声明公开出口时存在。

统一骨架示例：

~~~python
"""模块功能：在母港主页执行页面识别和用户操作。

上层调用：
- application.ui.navigation：调用页面导航和回退。
- business.logistics：调用母港相关业务入口。

下层依赖：
- common.ui.interaction：提供页面点击和等待。
- common.vision：提供页面识别。

from autowsgr.common.types import PageName

from autowsgr.application.ui.controller.home_page import constants, recognition

        self._ctx = ctx

__all__ = ['HomePage']
~~~

上层调用和下层依赖只列直接关系，路径从 `autowsgr` 的下一层开始书写，不写
`autowsgr.` 前缀，也不列举间接调用方。

样例只展示通用编排，不表示所有模块都必须拥有 constants.py、recognition.py、
页面类或 __all__。文件是否存在以及职责边界由对应模块专项规范决定。

## 4. 空行和视觉节奏

- 模块级 class、def、常量分区之间保留两个空行。
- 类内相邻方法之间保留一个空行。
- decorator 必须紧贴目标 class 或 def，中间不得插入空行。
- import 分组之间保留一个空行；同组内部不得插入空行。
- 连续空行不得超过两行，最终以 Ruff format 结果为准。
- 一个短函数内部不使用空行分割每条语句；只在阶段或职责真正变化时分段。
- 赋值、判断和与其紧密关联的错误处理必须保持在同一视觉块内。

## 5. Import 编排和使用规则

### 5.1 固定分组

import 必须按以下顺序出现：

1. __future__；
2. 标准库；
3. 第三方库；
4. 项目内部模块；
5. TYPE_CHECKING 块内的仅类型依赖。

Ruff/isort 负责组内排序。不得手工制造与自动排序冲突的分组。

### 5.2 绝对导入

- 项目内部必须使用以 autowsgr 开头的绝对导入。
- 禁止相对导入，包括 __init__.py。
- 禁止 import *。
- __init__.py 只允许导入稳定公开对象并声明 __all__，不得放业务实现。

### 5.3 导入模块还是对象

- 必须使用定义方当前真实、规范的包名、模块名和对象名；不得在导入处制造另一套名称。
- from ... import ... 只允许导入公开模块、类、函数和常量。一个文件只消费某模块的
  一两个稳定公开对象时，可以使用该形式。
- 一个文件消费同一子模块的多项能力时，必须导入模块并保留来源，例如
  constants.CLICK_SORTIE、recognition.read_chapter。
- 跨文件配置和识别实现应优先使用模块限定名，避免读者搜索定义来源。
- 禁止 from module import _private_name。确需在重构期间跨模块访问私有对象时，必须
  导入其所属模块并通过 module._private_name 访问，使所有权和私有边界保持可见。
- 不得通过导入别名、包级转出或复制实现，把私有对象伪装成公开 API。需要公开能力时，
  必须由原所属模块定义语义真实的公开对象。
- 不属于本项目定义的名称必须逐字节保持原样，不得为了统一风格改写：环境变量、协议
  字段、第三方 API 参数、CLI flag、持久化 key 和标准库协议签名。例如 `DSH_HOME`、
  `use_attribute_docstrings` 和 `Enum._missing_` 的 `value` 参数即使不符合本项目
  命名习惯也不改；本规范只约束自己起的名字。

### 5.4 别名

- 禁止使用 import ... as ... 或 from ... import ... as ... 把包、模块、类、函数或常量
  改成兼容名、缩写名或语义别名。
- 禁止把 ContextHandle 改名为 UIContext、GameContext 或 RuntimeContext 等旧类型，或用旧类名包装新类名。
- 同名冲突必须通过导入所属模块并使用模块限定名解决，不得再发明对象别名。
- 兼容旧名称必须建立职责明确、可单独删除的适配模块或兼容入口；不得用导入别名
  或包级转出代替兼容层。

### 5.5 TYPE_CHECKING 和局部导入

- 只用于类型注解、且运行时不需要的 import 必须进入 TYPE_CHECKING。
- 运行时使用的对象不得仅放在 TYPE_CHECKING。
- import 默认必须位于文件顶部。
- 局部 import 只允许解决已确认的循环依赖或延迟加载明确的可选重依赖。
- 每个局部 import 前必须有一行注释说明原因；不能用局部 import 掩盖错误依赖。

## 6. 常量和配置的编排位置

### 6.1 三类位置

维护者查找某项配置时，必须能够从拥有该业务的文件出发定位定义：文件专属参数就在
消费文件顶部，共享参数由该文件显式引用当前业务模块的 constants.py。不得要求维护者
到无明确业务归属的全局配置文件中搜索。

常量和静态配置必须按使用范围放置：

| 使用范围 | 位置 |
| --- | --- |
| 多个文件共享的静态业务数据、坐标、ROI、颜色或其他校准值 | 当前业务模块的 constants.py |
| 只被一个流程消费的时序、重试次数或流程阈值 | 流程消费文件顶部，首个 class/def 之前 |
| 只被一个识别或算法实现消费的置信度、采样次数或算法阈值 | 识别或算法文件顶部，首个 class/def 之前 |
| 只在一个短表达式中使用且语义显然的值 | 保留在局部表达式 |

不得为了“集中配置”把所有参数搬进一个全局 constants.py。不得在多个文件复制
同一常量；每个值必须只有一个定义源，其他文件只能引用该定义。

### 6.2 命名

- 模块常量使用 UPPER_SNAKE_CASE。
- 配置模型（`XXXConfig`）的字段与模块常量同规范，使用 UPPER_SNAKE_CASE；YAML 中的
  键名因此也是全大写。字段名带上所属能力的短前缀（`LOG_`、`SCRCPY_`、`DEVICE_`、
  `ADB_`），使同一份用户配置文件里的键不靠缩进层级也能自解释归位。
- 下划线只表达**可见性**，不表达重要性：一个模块级名字（常量、函数、类或模块级变量）
  只在定义它的文件内部使用，加前导下划线；被其他文件引用时，不加下划线。
- 因此 constants.py / config.py 中给同包或跨模块共享的校准数据与配置一律不加下划线；
  只在消费文件内部使用的阈值、探针、模式串和辅助函数一律加下划线。
- 出现在公开函数签名默认值里的配置常量视为公开配置，放在 constants.py / config.py。
- 名称必须同时表达业务对象和用途，不使用 DATA、CONFIG、VALUE、TIMEOUT 等
  脱离上下文的宽泛名称。
- 布尔常量必须使用 ENABLE_、ALLOW_、USE_ 或 REQUIRE_ 等明确前缀。
- 数量、时间、距离和阈值必须在名称或注释中写明单位。

### 6.3 分区和排序

- constants.py 必须按业务用途分区，例如页面点击、列表滑动、页面检测、OCR、
  颜色和模板；不得只按 Python 类型分区。
- 普通标量配置与屏幕坐标、ROI、颜色等校准数据必须使用不同的业务命名分区；
  校准值不得混入普通常量区，也不得在消费文件中重复定义。
- 同一语义的 x、y、z 或起点、终点参数必须相邻；轴参数固定按 x、y、z 排列。
- 常量按业务流程和页面顺序排列，不按名称字母排序。
- 一个常量组只有一两项时不单独创建装饰性分区。
- 文件配置区只允许静态参数和静态业务数据，不得存放上下文、设备对象、可变运行时
  状态或调度规则。

### 6.4 常量注释

- 每个非显然的常量或同质常量组必须说明业务用途、单位或校准来源。
- 简单说明使用行尾注释，整行不得超过 100 字符。
- 需要两行以上才能说明时，使用常量组上方的块注释，不堆叠多条行尾注释。
- 注释不得只重复名称，例如“主页超时时间”不是 HOME_READY_TIMEOUT 的有效说明。

### 6.5 坐标与识别资源

坐标、识别区域和识别模板属于静态校准数据，所有模块必须遵守：

- 坐标使用 `[0, 1]` 归一化值；同一语义轴的起点和终点必须相邻成组，不得散落在多个文件；
- **默认保留四位小数**。四位小数是默认可读格式，不是牺牲校准精度的绝对上限；
- 四位小数必须仍然覆盖被识别对象：**左、上边界向下取整，右、下边界向上取整**，
  保证识别区域不小于对应模板。仅做四舍五入会让区域小于模板，导致匹配直接失败；
- 取整后仍不满足覆盖要求时，保留必要精度，并在注释中写明来源分辨率或校准依据；
- 变更坐标后必须至少跑一次相关识别验证，确认目标在支持分辨率上的像素等价或明确偏移；
- 识别模板按实际消费模块归属，**目录名小写、模板文件名全大写**，名称表达用途与分辨率。

### 6.6 配置模型编排

配置模型是所有模块共用的整体传递结构，统一按本节编排，不允许 A 模块一个样、B 模块
一个样。

位置与粒度：

- 配置模型放在模块根目录的 `config.py`，深度最多两层
  （`autowsgr/<域>/<模块>/config.py`）；
- 聚合度高的域在域根放一个 `config.py` 聚合多个功能块
  （例如 `autowsgr/application/controller/config.py`）；
- 更深的子包不再单独建 config，配置向上合并到最近的模块根；
- 没有用户可改项时不建 config 文件，不为凑结构创建空模型。

文件骨架固定六段、顺序不得调整：模块 docstring（功能 / 上层调用 / 下层依赖 / 边界）→
`from __future__ import annotations` → imports → 模块级常量 → 配置类 → `__all__`。
模块级常量只放该配置域共享的默认值，不搬入模块业务常量。

类内编排固定四段：类 docstring → 字段 → 校验方法 →（结束），类内不出现其他成员：

- 类 docstring 一句话，写成“保存 X 模块的可覆盖配置。”；
- 字段名 `UPPER_SNAKE_CASE`，一行一个字段；
- 字段说明一律用行尾注释（`# 说明。`），超过 100 列时把注释移到字段上方；
- 字段不少于 6 个时按业务分组，分组标题使用 `# ── 分组名 ──`（见第 10 节）；
- 不可变默认值直接写在等号后；可变默认值使用 `Field(default_factory=...)`；
  需要取值约束时使用 `Field(default=..., ge=..., gt=..., allow_inf_nan=False)`；
- 子配置聚合字段使用 `Field(default_factory=XXXConfig)`；
- 同一文件存在多个配置模型时，被聚合的子配置在前、聚合配置在后，不按字母顺序排列。

校验方法：

- 放在全部字段之后，命名为 `_动词_字段`（`_parse_ship_name_map`、`_set_log_user_dir`）；
- `field_validator(mode='before')` 负责把外部宽容写法归一成声明类型；
- `model_validator(mode='after')` 负责补齐派生默认值；
- 单条数据格式错误时记录 warning 后跳过该条目，不让整棵树加载失败。

默认值与真值：

- 所有字段必须有默认值，缺字段的旧配置文件才能正常加载；
- 值一旦上浮进配置，模块内不再保留同名常量，配置默认值即唯一真值；
- 改字段名或删字段必须配迁移提示，走 `autowsgr.config_compat`；
- 上浮判据：换一台机器或换一个账号就需要修改的值才进配置；算法参数、坐标、颜色和
  识别阈值留在模块常量。

顶层树：`autowsgr.config.UserConfig` 只做聚合，每个模块配置占一个字段并全部使用
`Field(default_factory=...)`；字段顺序固定为基础设施在前、应用业务在后；新增模块配置
时在其中显式增加一条 import 和一个字段，不做自动发现或动态注册。

禁止项：

- 配置模型内不出现业务方法（查询、映射、计算）、文件 IO、设备访问和跨模块业务调用；
- 映射、解析规则由调用方直接使用 `.get(值, 默认值)`，不在配置模型上开业务方法。

## 7. 类型、类和函数的编排

### 7.1 模块级顺序

- 类型别名、枚举和轻量数据模型放在业务实现之前。
- 文件有一个主要公开类或函数时，该入口必须位于实现区域最前。
- 支撑公开入口的操作按入口调用顺序排列。
- 私有辅助函数放在所属功能区末尾；跨多个功能区使用时统一放在文件末尾。
- __all__ 位于全部定义之后；排序由 Ruff RUF022（unsorted-dunder-all）决定，以工具
  结果为准，不要求公开定义顺序。
- 禁止按字母顺序排列函数和方法。

### 7.2 类内顺序

类必须遵守以下阅读顺序：

1. __init__；
2. 最主要的公开业务入口；
3. 入口按执行顺序调用的检查、读取和动作；方法可见性由模块专项规范决定；
4. 返回、关闭或清理入口；
5. 私有实现和私有辅助。

如果类没有统一主流程，则按独立业务功能分区，每个分区内仍按
“公开入口 → 状态读取 → 动作 → 终态确认 → 私有辅助”排列。

### 7.3 纯识别和纯算法模块

不含业务编排的识别、解析或计算模块按数据变换顺序排列：

1. 数据模型和映射；
2. 规范化；
3. 纯解析；
4. 识别或计算入口；
5. 结果组合；
6. 私有辅助。

同一业务场景的 parse、recognize 和 calculate 函数必须在同一区域，不得按前缀
分散到文件各处。

### 7.4 公开入口与内部实现

模块对外公开的函数和方法必须表达一个允许调用方能够独立理解和处理的完整意图，
并通过参数、返回值或明确异常表达输入、结果和失败边界。只用于组合另一个公开入口的
中间步骤、页面原子动作或状态读取，默认使用私有命名。

调用方只能依赖模块公开入口的业务参数和结果，不得通过多个中间方法自行拼装模块内部
流程。测试、工具或调试代码的直接调用不构成生产公开 API；确需对外公开时，必须存在
真实调用方和独立业务契约。

## 8. Def 前缀和动作语义

函数和方法必须使用“动作动词 + 业务对象”。一个前缀只表达一种行为：

| 前缀 | 语义 |
| --- | --- |
| run_ | 运行一个完整任务或可独立业务用例 |
| execute_ | 执行已经构造完成的命令、计划或步骤 |
| enter_ | 进入一个明确页面、模式或业务状态 |
| navigate_to_ | 在多个已知状态之间完成导航 |
| go_to | 按目标进入页面：页面控制器对上层的导航契约，落点取自目标枚举 |
| go_back | 返回调用方约定的父状态 |
| check_ | 读取当前外部状态并判断，不产生业务副作用 |
| is_ | 对已经持有的值执行纯布尔判断，不进行 I/O |
| has_ | 对集合、模型或缓存执行纯存在性判断 |
| can_ / should_ | 表达纯规则判断，不执行动作 |
| read_ | 从当前输入或外部状态读取事实 |
| recognize_ | 从图像、OCR 或其他感知输入提取结构化事实 |
| parse_ | 将文本或结构数据纯转换为模型或值 |
| normalize_ | 统一格式，不改变业务含义 |
| convert_ | 在两种明确表示之间转换 |
| calculate_ | 执行无副作用计算 |
| get_ | 返回对象已经拥有的值，不代替 check_ 或 read_ |
| load_ / save_ | 读取或持久化外部数据 |
| build_ | 根据已有输入组装新值，不持有后续生命周期 |
| create_ | 创建具有独立身份或生命周期的对象 |
| open_ / close_ | 打开或关闭页面内对象并确认目标状态 |
| click_ | 执行一个明确业务对象的原子点击 |
| select_ | 完成一个选项、目标或对象的选择 |
| confirm_ / cancel_ | 确认或取消有业务含义的操作 |
| dismiss_ | 关闭提示、动画或非业务弹窗 |
| wait_ | 等待一个写入名称的明确终态 |
| handle_ | 处理一个明确事件、阶段或分支 |

强制要求：

- 同一业务动作不得混用 check_、is_、has_ 和 get_。
- **is_ 只用于对已经持有的值做纯判断。凡是要读屏幕、读文件或发起其他 I/O 才能得出结论的，
  一律使用 read_ 或 recognize_，例如读页面身份用 read_home_page，不得写成 is_home_page_visible。**
- check_ 方法不得改变页面或业务状态；会产生动作时必须使用动作动词。
- parse_、normalize_、convert_ 和 calculate_ 必须保持纯函数语义。
- click_ 只表示原子交互；包含查找、点击、等待和复查的完整流程必须使用业务动词。
- wait_ 名称必须包含等待目标，禁止 wait_ready、wait_done 等脱离上下文的名称。
- 私有实现使用前导下划线；没有外部消费者的函数不得使用公开命名。
- 禁止 process、do、manage、handle_data、utils 等无法判断行为的宽泛名称。
- 布尔值必须读起来像判断，使用 is_、has_、can_、should_ 或 need_ 前缀；集合使用复数。
- 参数必须携带语义而不是形状：使用 retry_limit、config_path、session_id，不使用
  n、p、s、cfg、tmp 一类只为省按键的名字。

## 9. 业务语义命名一致性

### 9.1 单一词汇

新增模块或重命名功能前，必须确定一个业务概念的规范英文名和中文名。确定后，
以下位置必须使用同一词根：

- 目录；
- 模块和文件；
- class、enum 和数据模型；
- public def 和关键 private def；
- 常量和配置 key；
- 模板、资源和日志前缀；
- 注释、docstring 和用户可见文档。

### 9.2 Home/Main 示例

如果业务概念是母港主页，必须统一使用：

~~~text
home_page/
HomePage
PageName.HOME
home_*
主页
~~~

同一概念不得再使用 main_page、MainPage、PageName.MAIN 或“主界面”。main.py
只表示程序入口时才能使用 main；它不能替代 home 的业务语义。

### 9.3 文件名和目录上下文

- 业务目录必须使用业务概念，例如 bath_page、battle_page、campaign。
- page.py、constants.py、recognition.py、models.py 等技术职责名只有在父目录已经
  提供完整业务上下文时才能使用。
- 顶层或业务根目录禁止使用 utils.py、helpers.py、common.py、manager.py、
  misc.py 等无法表达所有权的名称。
- 一个文件包含多个无法用同一业务动词描述的职责时，必须按职责拆分或明确归属，
  不能用宽泛文件名遮盖。
- 单复数必须与对象语义一致：单一实体使用单数，集合或注册表使用复数。
- 除项目认可术语外，不新增只有作者理解的缩写。当前白名单为：OCR、ROI、YAML、
  API、E2E、ID、URL、HTTP、JSON、UI、RGB、BGR、PNG、ADB，以及项目既有词汇 ctx、
  _log、ctrl。名单只增不减；新增术语必须在同一变更中补进本节。

### 9.4 重命名

- 重命名前必须先 grep 每一个调用方，包括测试、工具、模板、文档和日志引用，确认完整
  影响面再动手；不允许边改边找。
- 重命名必须同步更新定义、导入、调用、常量、枚举、模板、日志、注释和文档。
- 禁止保留旧名称别名来隐藏未完成迁移。
- 新旧名称确实表达不同概念时，必须在相邻注释或模块专项规范中写明差异。

### 9.5 变量和参数命名

- 有具体名词可用时，不使用 data、info、obj、val、temp、thing、result 等脱离业务的
  名字。
- value 只允许出现在三行以内的小作用域；公开参数、公开属性和跨多行的局部变量必须使用
  业务名，例如 yaml_mapping 而不是 data、pressure_raw 而不是 value。
- 模块级变量、函数参数和返回值必须写全拼；只有 9.3 白名单内的缩写可以使用。

## 10. 功能区域分割线

长模块、长类和 constants.py 必须使用业务区域分割线：

~~~python
# ── 页面识别 ────────────────────────────────────────────────────────────────
~~~

类内分割线缩进一级：

~~~python
    # ── 出征准备流程 ────────────────────────────────────────────────────────
~~~

格式要求：

- 固定使用“#、空格、两个短横线、空格、业务名称、空格、填充线”结构。
- 分割线整行显示宽度固定为 78 列（东亚全角字符按 2 列计），模块级和类内使用同一总宽；
  类内缩进从填充线长度中扣除。
- 同一文件内所有分割线必须等宽，不允许出现第二种宽度。
- 标题必须是业务功能或流程阶段，例如“页面识别”“章节选择”“修理浮层”。
- 禁止使用“公共方法”“私有方法”“工具函数”“其他”“辅助”等语法或容器名称。
- 一个区域必须包含一个完整职责；单个短函数不得独占一个分区。
- 模块级分区前后保留两个空行，类内分区前后按方法空行规则处理。
- 短文件职责单一时不得为了形式添加分割线。

## 11. 注释的语言和格式

### 11.1 语言

- 业务注释和 docstring 使用简洁中文，代码标识符保持英文。
- 一个业务概念必须使用规范中文名，不得混用“浴室/浴场”“主页/主界面”等同义词。
- 英文技术术语只在没有稳定中文表达或项目已统一采用时保留。
- 完整句子以中文句号结束；分割线标题不加标点。

### 11.2 长度

- 模块 docstring 按四段式说明职责、直接调用方、直接依赖方和边界；每一段只保留必要信息。
- class docstring 默认一行且不超过 100 字符；构造契约复杂时最多 8 个非空行。
- 函数 docstring 默认最多 15 个非空行；每个参数说明最多 2 行。
- 单条独立注释默认一行，最长不得超过 100 字符。
- 一个判断原因最多使用连续 2 行注释；仍无法说明时，应重构命名或移入专项文档。
- 禁止在 docstring 中列出间接调用链、完整依赖树、历史提交和易变化的阈值。

长度上限不是删除必要业务契约的理由。超过上限时必须优先改进命名、拆分流程，
或把稳定设计说明放入模块专项规范，不能把长篇背景塞回代码。

## 12. Docstring

### 12.1 模块和类

- 模块 docstring 必须说明模块功能、直接上层调用、直接下层依赖和边界，不使用 Args、Returns、Raises。
- class docstring 一句话说明对象代表什么或负责什么。
- 只有构造参数或公开属性不明显时，class docstring 才增加 Google 风格 Args 或
  Attributes。

### 12.2 函数和方法

公共函数、公共方法和复杂私有函数必须使用精简 Google 风格，段落顺序固定为：

1. 一句摘要；
2. 必要的稳定业务补充；
3. Args；
4. Returns；
5. Raises；
6. Yields。

只写实际存在的段落。无参数函数不得写 Args: None；返回 None 时不得写
Returns: None；函数不抛出调用方需要处理的异常时不得创建空 Raises。

~~~python
def recognize_chapter(screen: np.ndarray) -> int:
    """识别当前选中的章节。

    Args:
        screen: 地图页面 RGB 截图。

    Returns:
        当前章节编号。

    Raises:
        RecognitionError: 截图中没有可确认的章节特征。
    """
~~~

摘要必须说明动作和结果，不重复函数名。参数说明必须写业务含义和必要格式；
Returns 写业务结果；Raises 写调用方需要处理的失败。

docstring 不得写具体重试次数、timeout 数值、坐标或其他由常量控制的细节，避免
实现变化后说明失真。

## 13. 行内注释和流程注释

### 13.1 必须增加注释的节点

以下位置必须有注释：

- 多阶段流程的每个主要阶段；
- 非显然分支及其选择原因；
- 状态转换前后的预期状态；
- fail-closed、提前返回和中断点；
- retry、fallback、兼容路径及其触发条件；
- 不可逆操作或会消耗游戏资源的操作；
- 硬件、分辨率、坐标、ROI、颜色和 OCR 校准依据；
- 为避免竞态、重复点击、错误页面或数据覆盖而采取的顺序约束；
- 临时 workaround 的触发、移除条件和验证依据。

### 13.2 多阶段流程

线性业务流程必须在对应代码前使用连续编号：

~~~python
# 1. 确认当前页面，避免在未知状态点击。
...

# 2. 执行目标动作。
...

# 3. 等待并确认目标终态。
...
~~~

编号只描述业务阶段，不描述 Python 语句。流程插入或删除阶段后必须同步更新编号。

### 13.3 判断原因

注释放在被解释代码之前：

~~~python
# 浮层会遮挡基础特征，因此命中浮层也视为仍在浴室页面。
if overlay is not None:
    return PageMatch(name=name, matched=True)
~~~

不得写：

~~~python
# 如果 overlay 不是 None 就返回 matched True。
if overlay is not None:
    return PageMatch(name=name, matched=True)
~~~

### 13.4 禁止的注释

- 逐行翻译代码；
- 与当前行为无关的历史背景；
- 记录容易变化的数字而不引用常量；
- 使用“临时处理”“特殊情况”“先这样”等无法行动的描述；
- 使用 TODO 代替明确的问题、owner 和完成条件；
- 用大段注释解释本应拆分或重新命名的代码；
- 重复类型注解、变量名或函数名已经表达的信息。

### 13.5 刻意简化标记

已知的刻意简化必须留下 `ponytail:` 标记，写明保留原因、已知上限和升级条件：

~~~python
# ponytail: 只支持单显示器；出现多显示器需求时改成遍历 display_id。
~~~

- 标记写成一行可行动的完整说明，格式为 `# ponytail: <已知上限>；<升级条件>`。
- `ponytail:` 标记不属于 13.4 禁止的模糊描述；但只在确实放弃通用做法时使用。
- 达到升级条件、重新实现该能力时，连同标记一起删除。

## 14. 日志和可见文本中的语义

本节规定 `autowsgr` 生产代码的日志格式、级别、持有者和必要节点。
日志必须让维护者从一条记录中判断模块、职责位置、具体动作和结果或原因。

### 14.1 基本格式

日志从左到右使用以下结构：

~~~text
[模块名] 位置 连接符 动作：附加信息
~~~

以下示例均为 `INFO` 级别日志，使用中文业务字段和中文业务结果：

~~~text
[UI] 食堂 → 选菜谱：编号=2
[UI] 食堂 → 取消做菜：结果=取消，原因=已有料理
[COMBAT] 状态机 → 进夜战：节点=B
[VISION] 舰船识别 → 识别舰船：名称=岛风，置信度=0.94
[DEVICE] 设备控制 → 启模拟：结果=成功
~~~

规则如下：

- `[模块名]` 取 `autowsgr.A.B` 中的 `B`，统一使用大写；例如 `autowsgr.application.ui`
  使用 `[UI]`，`autowsgr.business.combat` 使用 `[COMBAT]`。
- `[模块名]` 与“位置”之间只保留一个空格，不放连接符。
- 有具体页面时，“位置”使用简短中文页面名，建议不超过 4 个字；没有页面时使用
  职责名，例如“状态机”“设备控制”“配置加载”“舰船识别”。
- 动作使用简短业务动词，建议控制在 2～4 个字，例如“选菜谱”“关弹窗”“回后院”“进夜战”。
- `→` 默认表示动作或状态转移；`：`用于事实、结果或附加说明；` - `只用于没有方向性的
  普通说明，不得放在 `[模块名]` 与“位置”之间。
- 固定语义层（模块名、位置、动作和必要的结果/原因说明）使用统一中文业务词汇；`INFO`
  日志中的业务附加信息按上述示例使用中文字段和中文业务结果。技术值、字符串原文、路径、
  坐标、枚举、阈值、置信度和单位可保留原文，不得为了翻译丢失排障所需的准确性。`DEBUG`
  优先保留源代码中的真实变量名和运行时实际值，使用
  `变量名=值` 表达，例如 `current='DAY'`、`candidates=['NIGHT', 'RESULT']`、
  `threshold=3`；同类诊断必须保持变量名和表示方式稳定。
- 代码层使用日志库占位符，不使用 f-string；需要区分字符串原文时使用 `!r`。只记录能够
  解释判断、识别、重试、fallback 或技术映射的变量，不得把所有局部变量或无界对象倾倒进
  日志。
- 使用 `get_logger()` 创建模块 logger，日志消息使用占位符，不使用 f-string；logger channel
  用于过滤，不能替代日志中的可读模块名和职责位置。
- 日志、异常文本、注释和函数名必须使用同一套业务词汇，不得混用未经定义差异的同义词。
- 不得输出 Token、密钥、用户配置全文、隐私日志、原始截图或无必要的完整运行时对象。

### 14.2 日志级别

| 级别 | 使用场景 |
|---|---|
| `DEBUG` | 内部诊断事实：识别候选、OCR 原文、置信度、真实变量、重试过程、复检结果和分支判断依据 |
| `INFO` | 用户可感知的关键动作、页面状态转换和已确认的正常结果 |
| `WARNING` | 预期被破坏且当前路径已降级，但仍能通过重试、回退、安全跳过或人工处理继续 |
| `ERROR` | 当前目标无法产生要求的结果、状态或契约不可再信任，必须终止、失败退出或安全拒绝 |

本规范只定义以上四个业务级别。日志库或旧代码中的 `TRACE` 归入 `DEBUG`，不作为新代码
级别；`SUCCESS` 不单独使用，正常完成使用 `INFO` 并带 `结果=成功`；异常堆栈不是独立
级别，只在负责收口的 `ERROR` 边界记录，避免多层重复记录。

`DEBUG` 的附加信息应优先回答“为什么做出这个判断”，而不是重复播报动作。正常动作不因
“可能有用”而提升到 `DEBUG`；取消和次数不足必须明确记录结果，不能写成含义不明的“完成”。
高频识别、轮询和底层匹配日志必须有明确诊断价值，并限制文本、列表和对象的大小。

`WARNING` 必须同时说明“预期事实”“实际异常”和“当前后果或下一步处理”。附加信息优先
使用真实变量名和实际值，例如 `expected`、`actual`、`reason`、`attempt`、`max_attempts`、
`fallback`、`result` 或 `user_action`；不能只写“失败”“异常”“重试”等无法判断影响的
描述。异常是否存在不决定级别，仍能继续且行为已降级时才使用 `WARNING`。

普通自动重试、正常无通知、无任务或无可操作对象不单独使用 `WARNING`：前者使用 `DEBUG`，
后者使用 `DEBUG` 或 `INFO`。只有进入降级路径、达到有意义的重试边界、使用会改变行为的
fallback，或需要用户关注时才使用 `WARNING`。当前路径最终无法完成或无法继续时使用
`ERROR`。

`ERROR` 必须绑定明确的失败目标或不变量：要求的结果无法产生、页面或数据契约无法确认、
恢复路径也已失败，或继续执行会产生错误操作。附加信息优先使用真实变量名和实际值，按需
包含 `operation`、`expected`、`actual`、`reason`、`error_type`、`error`、`attempt`、
`max_attempts`、`fallback`、`result` 和 `next_action`。日志必须说明最终后果，不能只写
“失败”“异常”或“任务出错”。

ERROR 动作使用能够说明终态的短语：

| 动作 | 使用场景 |
|---|---|
| `失败` | 目标操作最终没有完成 |
| `终止` | 当前任务或流程被迫停止 |
| `拒绝` | 输入、规则或状态不安全，拒绝继续操作 |
| `超时` | 等待预算耗尽，目标状态仍未出现 |
| `恢复失败` | 原操作失败，恢复路径也失败 |
| `校验失败` | 最终结果不满足业务约束 |

恢复仍然可能成功时使用 `WARNING`；只有恢复耗尽、最终结果无法保证或流程必须停止时才使用
`ERROR`。异常堆栈是附加信息，不是独立级别；只在 ERROR 收口处记录，避免同一异常被多层
重复记录。

ERROR 示例：

~~~text
[UI] 页面导航 → 终止：target='home', current='battle', attempt=3, max_attempts=3, reason='page_not_reached', result='failed', next_action='restart'
[COMBAT] 编队 → 拒绝：rule='strict', candidates=['A', 'B'], reason='no_valid_assignment', result='not_started'
[DEVICE] 视频流 → 恢复失败：attempt=3, max_attempts=3, error_type='ConnectionError', error='stream_lost', next_action='disconnect'
~~~

WARNING 示例：

~~~text
[UI] 章节导航 → 重试：expected=5, actual=4, attempt=2, max_attempts=3, reason='OCR mismatch'
[VISION] 舰名识别 → 拒绝：text='岛风', candidates=['岛风', '岛风改'], reason='ambiguous'
[DEVICE] 视频流 → 重连：attempt=2, max_attempts=3, reason='stream_lost', result='retry'
~~~

DEBUG 示例：

~~~text
[UI] 页面识别 → 匹配结果：best='home'，score=0.932，candidates=5，hits=['home']
[VISION] OCR → 模糊匹配：text='岛风'，best='岛风'，distance=0，threshold=3
[COMBAT] 状态机 → 评估转移：last_phase='DAY'，action='select'，candidates=['NIGHT', 'RESULT']
~~~

### 14.3 日志持有者与代码落点

日志放在拥有该动作、状态或结果判断的函数中：

- 页面方法记录自己执行的页面动作，以及自己直接确认的页面终态。
- `workflow.py` 或状态机记录多步骤流程的开始、分支决策和整体结果，不重复打印每个子动作。
- 识别模块只记录识别事实、最终汇总和无法确认的原因，不记录设备点击或页面跳转。
- 导航 service 记录跨多个页面的完整路径；单个页面的 `go_back()` 或页面边动作由页面方法记录，
  导航 service 不重复记录同一条边。
- 纯转发、参数转换和没有独立业务语义的辅助函数默认不记录。

一个流程包含多个方法时，遵守“流程记生命周期，方法记自有动作，判断者记结果”：

~~~text
流程函数：开始、分支、整体结果
页面方法：页面动作、直接页面终态
识别方法：识别事实、识别失败
~~~

日志语句的具体落点遵循以下执行顺序：

~~~text
读取事实 → 做判断 → 执行业务动作 → 确认终态 → 恢复或终止
  DEBUG       DEBUG          INFO           INFO       WARNING / ERROR
~~~

| 代码节点 | 级别 | 具体落点 |
|---|---|---|
| 判断或识别依据已经形成，条件判断前 | `DEBUG` | 紧邻使用这些变量进行条件判断、候选选择或状态转移的位置 |
| 重要业务动作开始前 | `INFO` | 紧邻业务副作用之前，使用“开始”或“尝试”表达意图；普通原子操作不强制记录 |
| 动作执行且目标终态确认后 | `INFO` | 紧邻确认成功之后，使用“完成”“成功”或 `结果=成功` 表达已确认结果 |
| 检测到异常且决定恢复、降级或跳过前 | `WARNING` | 紧邻 `retry`、`fallback`、安全跳过或降级动作之前，说明异常事实和后果 |
| 恢复耗尽且即将失败退出 | `ERROR` | 紧邻 `raise` 或失败返回之前，说明最终失败、影响和后续处理 |

具体规则如下：

- `INFO` 的“开始/尝试”必须放在动作前；“完成/成功”必须放在动作执行且页面、业务或
  资源终态确认后。一个动作只需要一条日志时，优先记录确认后的结果。
- `DEBUG` 放在诊断事实已经产生、且即将参与判断的位置，不放在每个函数入口或出口；普通
  重试可以记录 DEBUG，但不得把每次截图、每一帧或每个像素都无界输出。
- `WARNING` 放在异常分支已经确定、恢复动作尚未执行的位置。若恢复仍可能成功，不得提前
  使用 `ERROR`；恢复成功后不再为同一事件追加 ERROR。
- `ERROR` 只能表示最终无法完成、状态或契约不可再信任、必须终止或安全拒绝。捕获异常后
  仍会重试或回退时，不得在该处记录 ERROR。
- 日志文本必须与实际执行阶段一致：动作前不能写“成功”，仍会继续恢复时不能写“终止”。
- 原子操作函数只执行点击、滑动或设备调用时，默认不记录业务级日志；只有拥有下层没有的
  唯一技术事实时才记录窄范围 DEBUG。已由通用基础设施记录的坐标、截图或连接信息不得重复记录。

#### 必须记录的节点

以下节点必须有能定位业务语义的日志：

- 页面进入、离开、返回和跨页面状态转换；
- 用户可感知的选择、切换、确认、取消和关闭；
- 购买、修理、做菜等会改变状态或消耗资源的动作；
- 非显然分支、fallback、重试和异常恢复的进入原因；
- 已确认的成功、取消、次数不足、超时和失败终态。

#### 不要求单独记录的节点

以下节点不要求单独记录：

- 每一帧截图或每一次普通轮询；
- 被上层业务动作完整描述的单纯坐标点击；
- 纯布尔判断、数据转换和没有独立业务含义的私有辅助函数。

`common/system/logger.py` 作为日志基础设施允许使用 bootstrap 例外，但必须在本模块规则中说明。
`common/vision/easyocr_models_cli.py` 没有页面时使用 `[VISION]`，并以“模型下载”“模型校验”
等职责作为位置，不得省略模块名。
