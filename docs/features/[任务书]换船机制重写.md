### 0.1 核心判断：业务逻辑保持一致，重写代码结构

用户 2026-11-02 三轮明确：

> 换船逻辑是我亲自设计的，从业务编排上已经很稳定了，我不想修改太多，

> 我修正一下，**重写的前提是业务逻辑保持一致，重写代码结构**。

这两句合起来是本任务书的唯一判据：

| 保持不变 | 允许重写 |
| --- | --- |
| 换船策略、分配算法、11 步顺序、重试次数、失败处理 | 文件划分、函数边界、参数形态、类结构 |

凡是行为变化，都必须能在任务书里找到授权依据，否则视为回归。

**解耦判据**：把旧文件里每一行问一句「这是判断，还是动作？」——
判断留 `fleet_select`，动作搬进 `controller`。

## 1. 分层与依赖

```text
business/                      业务层：决定要哪六条船、打不打
        │  垂直调用
        ▼
application/
  ├── navigation/              导航器：只负责「到哪个页面」
  ├── fleet_select/            ★ 新增：换船业务编排 + 舰名资产
  │       │  平行调用
  │       ▼
  └── controller/              控制器：只认页面、只做单次点击与单次识别
          │  垂直调用
          ▼
      common/vision            识别能力：模板、OCR、像素
```

三条硬规矩：

1. `fleet_select` **不直接调用 `common.vision`**，一切识别都经 `controller` 的 checker。
2. `controller` **不做流程编排**：一个方法只做一次点击或一次识别，不写「先读、再判、再重试」。
3. 导航器**不感知换船**：把用户送到准备页就结束。

【解耦判据】把旧文件里每一行问一句「这是判断，还是动作？」——
判断留在 `fleet_select`，动作搬进 `controller`。

### 4.2 R3 的落地要求（用户 2026-11-02 第 3 条）

> 用 task type 限制，或者业务层限制，传了对应的参数就报错，我们 application 层不做处理。

落地为**模式枚举 + 入口参数校验**，底层不做页面判断：

```python
class FleetSelectMode(StrEnum):
    """换船模式。决定走哪一套编排，也决定哪些能力可用。"""

    NORMAL = 'normal'        # 普通出征 / 活动 / 演习
    DECISIVE = 'decisive'
    CAMPAIGN = 'campaign'
```

规则：

1. `adjust_fleet(ctx, *, mode: FleetSelectMode, ...)` 是唯一入口，**入口处校验参数组合**；
2. 传入与模式不匹配的字段（例如 `mode=CAMPAIGN` 却传 `fleet_id`）**直接抛 `ValueError`**；
3. `controller` 的 `click_team_tab` / `read_team_tab` **不做页面判断**、不加断言，
   它们只是「点这个位置」「读这个位置」——按用户要求，application 层不做处理；
4. 模式 → 页面 的对应关系由调用方（`fleet_select` 的 `__init__.py`）保证。

这样既满足「传错参数立刻报错」，又不会在 page 层塞业务判断。

## 5. 出征页船只识别（R4）

### 5.1 读什么

准备页六槽，每槽四个事实：

| 事实 | 来源 | 谁负责 | 备注 |
| --- | --- | --- | --- |
| 槽位有没有船 | 血条左端像素 | controller | 复用 `quick_maintenance/checker.py` 已实机标定的五个参考色 |
| 舰名**原文** | 六槽横向整条 OCR + 按 bbox 中心归槽 | **controller 只给原文** | 不给舰名，不给比对结果 |
| 舰名**归一** | 原文 → `shipnames.yaml` 比对 → 标准舰名 | **fleet_select** | 清单是它的资产 |
| 舰种 | 逐槽窄框 OCR → `ShipType` 枚举匹配 | controller | 枚举是公共词汇，不是业务清单 |
| 等级 | 逐槽窄框 OCR + 数字纠错 | controller | `LV.110` → `110` |

### 5.1.1 识别与比对的分界线（用户 2026-11-02 第 5 条）

> controller 只负责识别，比对是 fleet select 的事情。

分界线定在**是否依赖业务清单**：

| 动作 | 例子 | 归谁 |
| --- | --- | --- |
| 形态归一化 | 去括号国籍、放大、灰度、OTSU、I/O/S/B→0/1/5/8 | controller |
| 枚举匹配 | `'轻母'` → `ShipType.CVL` | controller（枚举在 `controller/types.py`，不是清单） |
| **清单比对** | `'维内托'` → 全库 3000 条舰名里查到 `'维托里奥·维内托'` | **fleet_select** |

因此 `controller` **不 import `fleet_select` 的任何东西**，反向依赖被彻底消除（原 Q7）。

### 5.2 复用哪些旧原语

| 原语 | 作用 | 去向 |
| --- | --- | --- |
| `extract_ship_type_from_text` | 去括号国籍、去空格，再对 `ShipType.value` 严格匹配 | `ship_recognition/checker.py` 私有 |
| `upscale_text_crop` / `prepare_level_crop` | OCR 前放大 / 灰度+OTSU | `ship_recognition/checker.py` 私有 |
| `parse_fleet_level` / `normalize_level_digits` | `LV.110` → `110`，I/O/S/B 数字纠错 | `ship_recognition/checker.py` 私有 |
| `LEVEL_OCR_ALLOWLIST` / `LEVEL_PATTERN` | OCR 字集与正则 | `ship_recognition/constants.py` |
| `normalize_ship_name` / `ship_name_identity` / `expand_ship_name_candidates` / `SHIPNAME_GROUPS` | 舰名归一化与别名 | **`fleet_select/names.py`**（见 §11 Q2 结论） |
| `classify_blood` | 血条颜色 → 损伤态 | **不搬**，用 `quick_maintenance` 已实机标定的版本 |

注意 `ship_recognition/checker.py` 读舰名时**要对齐舰名池**，所以它会 import
`fleet_select.names`。这形成 `controller → fleet_select` 的反向依赖，
必须在落地时处理（见 §11 Q7）。

| --- | --- |
| `FLEET_SLOT_X_CENTERS` | 六个物理槽位的横向中心 |
| `FLEET_NAME_STRIP_Y` | 舰名横带（整条 OCR 用） |
| `SHIP_TYPE_CROP` | 六槽舰种窄框 |
| `SHIP_LEVEL_CROP` | 六槽等级窄框 |

| `BLOOD_BAR_PROBE` | 六槽血条采样点（旧值 x 0.0586/0.1750/0.2915/0.4086/0.5250/0.6415, y 0.5959） |

这些值来自旧 YAML 校准，**落地前必须用当前实机帧逐条复核**。

### 5.4 出口形态

**controller 侧**（`ship_recognition/checker.py`）只给识别事实，舰名是**原文**：

```python
@dataclass(frozen=True, slots=True)
class FleetRecognition:
    """出征准备页六槽的识别事实，舰名未与任何清单比对。"""

    name_texts: tuple[str | None, ...]      # OCR 原文，槽位 1–6
    occupied: tuple[bool, ...]              # 血条是否读到有船
    ship_types: tuple[ShipType | None, ...]
    ship_levels: tuple[int | None, ...]

def read_fleet_recognition(ctx: ContextHandle, *, attempts: int = 3) -> FleetRecognition: ...
```

**fleet_select 侧**（`battle_preparation/__init__.py` 或 `snapshot.py`）把原文比对成标准舰名：

```python
@dataclass(frozen=True, slots=True)
class FleetSnapshot:
    names: tuple[str | None, ...]
    occupied: tuple[bool, ...]
    ship_types: tuple[ShipType | None, ...] = ...
    ship_levels: tuple[int | None, ...] = ...

def read_fleet_snapshot(ctx: ContextHandle, *, attempts: int = 3) -> FleetSnapshot: ...
```

槽位号从 1 开始，识别失败的槽位仍出现在结果里、对应字段为 `None`。
`ShipsService` / `ShipTaskType` 的「按任务类型路由」形态**取消**：只有一个域时它是空转抽象。

## 9. 保留的旧经验（务必写进新实现）

旧 `fleet_adjustment/workflow.py` 顶部把 11 步流程写成了 docstring，是上一轮实机踩出来的，逐条保留：

1. 保留可用主选，并为 candidate-only 槽位分配唯一备选；
2. 全部主选与备选作为全局 OCR 补救上下文；
3. 结合血条探针区分「空槽」与「有船但没识别出来」；
4. OCR 当前舰队，candidate-only 优先复用未被主选占用的已有舰船；
5. 先补齐主选，再处理 fallback；
6. 主选失败时重新做全局唯一分配，**不局部抢占**；
7. **先替换目标舰船，再删除多余** —— 否则会出现一队为空；
8. 删除时内存同步做槽位压缩；
9. 成员集合完整后，才做拖拽调序；
10. 再次 OCR 验证，漏识别的槽位保留已确认结果；
11. 验证失败只修正错误槽位，最多两次（`MAX_SET_RETRIES = 2`）。

以上只属于 `normal.py`。决战与战役是「一萝卜一坑」，不走这套分配算法。
