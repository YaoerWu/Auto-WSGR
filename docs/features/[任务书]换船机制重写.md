## 1. 分层与依赖

```text
business/                      业务层：决定要哪六条船、打不打
        │  垂直调用
        ▼
application/
  ├── navigation/              导航器：只负责「到哪个页面」
  ├── fleet_select/            ★ 新增：换船业务编排 + 舰名资产（内部四层见 §3）
  │       │  平行调用
  │       ▼
  └── controller/              控制器：只认页面、只做单次点击与单次识别
          │  垂直调用
          ▼
      common/vision            识别能力：模板、OCR、像素
```

三条硬规矩：

1. `fleet_select` **不直接调用 `common.vision`**，一切识别都经 `controller` 的 checker。
2. `controller` **不做流程编排**：一个方法只做一次点击或一次识别，不写「先读、再判、再重试」。
3. 导航器**不感知换船**：把用户送到准备页就结束。

【解耦判据】把旧文件里每一行问一句「这是判断，还是动作？」——
判断留在 `fleet_select`，动作搬进 `controller`。

## 3. 目标结构（四层，用户 2026-11-02 定稿）

用户对 `fleet_select` 内部定了四层：

> 第一层：入口层（是 service，不是 workflow），为业务层提供服务，业务层通过入参调用；
> 第二层：组装层（models 目录），组装具体动作，因为流程大相径庭、只有部分差异；
> 第三层：实现层（operation），一个个单独的方法，调用 checker 和 page，并通过规则层做后处理；
> 第四层：后处理层（rules），对 OCR 结果做后处理，还要对外提供 config。

| 层 | 位置 | 职责 | 不许做 |
| --- | --- | --- | --- |
| 入口 | `fleet_select/service.py` | `adjust_fleet` 按 `mode` 分发，校验参数组合 | 不含任何换船步骤 |
| 公共 | `fleet_select/types.py`、`fleet_select/constants.py` | 模式、规则、快照数据契约；流程节奏参数 | 不含判断逻辑 |
| 组装 | `fleet_select/models/*.py` | 把实现层的动作按模式串起来 | 不直接调 page、不判断规则细节 |
| 实现 | `fleet_select/operation/*.py` | 读快照、选船/移除、成员集合对齐、切队 | 不决定用哪套模式、不做整队校验 |
| 后处理 | `fleet_select/rules/*.py` | 舰名表、OCR 后处理、编队算法、约束判定 | 不读图、不点击 |

```text
autowsgr/application/
├── fleet_select/
│   ├── __init__.py                  # 出口：只导出 adjust_fleet
│   ├── service.py                   # 第一层：入口，按 mode 分发
│   ├── types.py                     # FleetSelectMode / ShipSelector / FleetSlotRule / FleetSnapshot
│   ├── constants.py                 # 流程节奏参数（重试次数、各步等待）
│   ├── rules/                       # 第四层：后处理
│   │   ├── constants.py             # 识别文字形态（国籍括号、等级形近字、匹配阈值）
│   │   ├── shipnames.py             # 舰名表、归一化、别名、模糊匹配
│   │   ├── ocr.py                   # OCR 原文 → 结构化事实（六槽快照、船池船卡）
│   │   ├── planner.py               # 编队算法：全局分配、校验、下一步动作
│   │   └── constraints.py           # 约束规则：规则归一化、船卡三态、战役舰种校验
│   ├── operation/                   # 第三层：实现
│   │   ├── fleet_snapshot.py        # 读六槽快照 + 补读缺字段 + merge_position
│   │   ├── ship_select.py           # 单槽选船 / 移除
│   │   ├── member_align.py          # FleetAligner：成员集合对齐与拖拽调序
│   │   └── team_select.py           # 切换 1-4 队
│   └── models/                      # 第二层：组装
│       ├── progress.py              # 进度上报
│       ├── normal.py                # 普通出征 / 活动 / 演习（11 步）
│       ├── decisive.py              # 决战：一萝卜一坑 + 可拖拽 + 无搜索框
│       └── campaign.py              # 战役：一萝卜一坑 + 不可拖拽 + 可先清空
│
└── controller/
    ├── types.py                     # ShipType（四方共用的公共词汇）
    └── sortie/battle_preparation/
        ├── checker.py               # 四准备页域探针 + 1-4 队页签
        ├── page.py                  # 返回 + 切队
        ├── constants.py
        └── ship_recognition/        # 出征页六槽识别：只给原始事实
            ├── checker.py           # read_ship_damage / types / levels / names
```

**切换队伍下沉到实现层**：切队是 page 动作，`models/normal.py` 只调用

`ShipType` 住在 `controller/types.py`：它被 `ship_recognition`、`exercise/checker.py`、

### 4.2 R3 的落地要求（用户 2026-11-02 第 3 条）

> 用 task type 限制，或者业务层限制，传了对应的参数就报错，我们 application 层不做处理。

落地为**模式枚举 + 入口参数校验**，底层不做页面判断：

```python
class FleetSelectMode(StrEnum):
    """换船模式。决定走哪一套编排，也决定哪些能力可用。"""

    NORMAL = 'normal'        # 普通出征 / 活动 / 演习
    DECISIVE = 'decisive'
    CAMPAIGN = 'campaign'
```

规则：

1. `adjust_fleet(ctx, *, mode: FleetSelectMode, ...)` 是唯一入口，**入口处校验参数组合**；
2. 传入与模式不匹配的字段（例如 `mode=CAMPAIGN` 却传 `fleet_id`）**直接抛 `ValueError`**；
3. `controller` 的 `click_team_tab` / `read_team_tab` **不做页面判断**、不加断言，
   它们只是「点这个位置」「读这个位置」——按用户要求，application 层不做处理；
4. 模式 → 页面 的对应关系由调用方（`fleet_select` 的 `__init__.py`）保证。

这样既满足「传错参数立刻报错」，又不会在 page 层塞业务判断。

## 5. 出征页船只识别（R4）

### 5.1 读什么

准备页六槽，每槽四个事实：

| 事实 | 来源 | 谁负责 | 备注 |
| --- | --- | --- | --- |
| 槽位有没有船 | 血条左端像素 | controller | 复用 `quick_maintenance/checker.py` 已实机标定的五个参考色 |
| 舰名**原文** | 六槽横向整条 OCR + 按 bbox 中心归槽 | **controller 只给原文** | 不给舰名，不给比对结果 |
| 舰名**归一** | 原文 → `shipnames.yaml` 比对 → 标准舰名 | **fleet_select** | 清单是它的资产 |
| 舰种 | 逐槽窄框 OCR → `ShipType` 枚举匹配 | controller | 枚举是公共词汇，不是业务清单 |
| 等级 | 逐槽窄框 OCR + 数字纠错 | controller | `LV.110` → `110` |

### 5.1.1 识别与比对的分界线（用户 2026-11-02 第 5 条）

> controller 只负责识别，比对是 fleet select 的事情。

分界线定在**是否依赖业务清单**：

| 动作 | 例子 | 归谁 |
| --- | --- | --- |
| 形态归一化 | 去括号国籍、放大、灰度、OTSU、I/O/S/B→0/1/5/8 | controller |
| 枚举匹配 | `'轻母'` → `ShipType.CVL` | controller（枚举在 `controller/types.py`，不是清单） |
| **清单比对** | `'维内托'` → 全库 3000 条舰名里查到 `'维托里奥·维内托'` | **fleet_select** |

因此 `controller` **不 import `fleet_select` 的任何东西**，反向依赖被彻底消除（原 Q7）。

### 5.2 复用哪些旧原语

| 原语 | 作用 | 去向 |
| --- | --- | --- |
| `extract_ship_type_from_text` | 去括号国籍、去空格，再对 `ShipType.value` 严格匹配 | `fleet_select/rules/ocr.py` 的 `parse_ship_type` |
| `upscale_text_crop` / `prepare_level_crop` | OCR 前放大 / 灰度+OTSU | **不搬**，`expect_ocr` 自带预处理 |
| `parse_fleet_level` / `normalize_level_digits` | `LV.110` → `110`，I/O/S/B 数字纠错 | `fleet_select/rules/ocr.py` 的 `parse_level` |
| `LEVEL_OCR_ALLOWLIST` / `LEVEL_PATTERN` | OCR 字集与正则 | `fleet_select/rules/constants.py`（`COUNTRY_SUFFIX_PATTERN`、`LEVEL_DIGIT_TRANSLATION`、`LEVEL_MIN/MAX`） |
| `normalize_ship_name` / `ship_name_identity` / `expand_ship_name_candidates` / `SHIPNAME_GROUPS` | 舰名归一化与别名 | **`fleet_select/rules/shipnames.py`**（见 §11 Q2 结论） |
| `classify_blood` | 血条颜色 → 损伤态 | **不搬**，用 `quick_maintenance` 已实机标定的版本 |

原先担心的「`ship_recognition/checker.py` 要对齐舰名池，形成 `controller → fleet_select`
反向依赖」已经不存在：controller 只返回 OCR 原文，清单比对全部在 `rules/ocr.py`（见 §5.1.1）。

### 5.3 六槽 ROI（旧常量，需按新图复核）

| 常量 | 内容 |
| --- | --- |
| `FLEET_SLOT_X_CENTERS` | 六个物理槽位的横向中心 |
| `FLEET_NAME_STRIP_Y` | 舰名横带（整条 OCR 用） |

## 9. 保留的旧经验（务必写进新实现）

旧 `fleet_adjustment/workflow.py` 顶部把 11 步流程写成了 docstring，是上一轮实机踩出来的，逐条保留：

1. 保留可用主选，并为 candidate-only 槽位分配唯一备选；
2. 全部主选与备选作为全局 OCR 补救上下文；
3. 结合血条探针区分「空槽」与「有船但没识别出来」；
4. OCR 当前舰队，candidate-only 优先复用未被主选占用的已有舰船；
5. 先补齐主选，再处理 fallback；
6. 主选失败时重新做全局唯一分配，**不局部抢占**；
7. **先替换目标舰船，再删除多余** —— 否则会出现一队为空；
8. 删除时内存同步做槽位压缩；
9. 成员集合完整后，才做拖拽调序；
10. 再次 OCR 验证，漏识别的槽位保留已确认结果；
11. 验证失败只修正错误槽位，最多两次（`MAX_SET_RETRIES = 2`）。

以上只属于 `normal.py`。决战与战役是「一萝卜一坑」，不走这套分配算法。

### 11.2 已实现的入口

```python
# autowsgr/application/fleet_select/service.py
def adjust_fleet(
    ctx: ContextHandle,
    *,
    mode: FleetSelectMode,
    fleet_rules: Sequence[FleetSlotRule | str | None],
    fleet_id: int | None = None,
    reset_fleet: bool = True,
    notify: Callable[[str, dict[str, object]], None] | None = None,

```

返回 `None` 表示「三轮用尽仍未满足规则」，由上层决定是跳过还是换一套编成；
参数越界、规则超长这类调用方错误才抛 `ValueError`。

| 组合 | 结果 |
| --- | --- |
